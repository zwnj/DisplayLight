技術調査レポート

Modern Standby環境で画面を暗くし、ローカル処理を継続する方法

類似事例とWindowsの公式仕様を照合すると、内蔵画面を汎用APIで物理消灯しながらWindowsを通常稼働状態に保つ確実な方法は確認できなかった。DisplayLightでは、既存の手動消灯を残しつつ、別の「作業継続モード」として画面を論理的にオンに保ち、最低輝度と黒画面を組み合わせる案が最も実装可能性が高い。

結論

SC_MONITORPOWERを使わない選択肢はある。ただし、内蔵パネルについては「物理的に消灯」と「Windows上の画面オン状態」を同時に満たす、機種非依存の公開APIは確認できなかった。最も堅実なのは、PowerRequestDisplayRequiredとPowerRequestSystemRequiredを保持し、内蔵画面を最低輝度へ下げ、必要なら黒い全画面表示を重ねる方式である。外部モニターにはDDC/CIによる物理電源制御を追加できるが、対応機器だけの任意機能とすべきである。[5][11][12]

重要な留保：Microsoftの仕様では、Modern Standbyの「Screen Off」と長期低電力の「Sleep」は別段階であり、画面オフ直後に必ずデスクトップアプリが停止するわけではない。今回の11秒での切断は、手動消灯経路、実際のPower Request、AC限定設定、OEM電源ポリシーを分離して再検証する必要がある。[1][2]

調査目的

本調査は、Modern Standby対応Windows PCで、画面を暗くまたは物理消灯しながら、Codexのような通常のデスクトップ処理とネットワーク接続を継続できるかを確認するものである。特に、DisplayLightが現在使っているSC_MONITORPOWER以外の方法、既存ツールの実装、利用者が遭遇した失敗例を対象とした。

技術的な挙動はMicrosoft LearnとMicrosoftの公開実装を根拠とし、GitHub Issue、Microsoft Q&A、Framework Community、Redditは再現例または利用者報告として区別した。コミュニティ投稿だけをWindows仕様の根拠にはしていない。

公式仕様から分かること

画面オフと長期低電力は同じ瞬間ではない

Modern Standbyセッションは画面オフから画面オンまでを包含するが、内部では通常処理を静めるScreen Off段階と、長期低電力のSleep段階に分かれる。Microsoftは、画面タイムアウト後もスリープタイムアウトまではアプリが通常どおり動作できる設計を説明している。[1][2]

含意

SC_MONITORPOWERのイベントが記録されたことだけでは、同時刻にDRIPSへ入りCodexが停止したとは断定できない。Screen Off段階を何が終了させたかを調べる必要がある。

Power RequestはScreen Off段階を延長できる

SystemRequiredなどの要求は、AC電源では解除されるまでScreen Off段階を延長できる。DC電源では、システムスリープタイムアウト経過後に最大5分という制限がある。低電力段階へ進むとDesktop Activity Moderatorが通常のデスクトップアプリを停止し、Adaptive Connected Standbyが通信を切断する場合がある。[3][4][5]

含意

DCで一晩中、画面オフのままローカルデスクトップ処理を保証する用途にSystemRequiredだけを使うことはできない。一方、画面オフ直後の11秒停止は5分上限だけでは説明できない。

DisplayRequiredは画面を論理的にオンへ保つ

PowerRequestDisplayRequiredは、無操作が続いてもセッションの画面をオンのまま維持する。システムスリープも防ぐにはSystemRequiredとの併用が必要である。MicrosoftのDC時5分制限の記述はSystem RequiredとExecution Requiredを対象としており、Display Requiredは画面オフ自体を発生させない経路になる。[5]

含意

画面をWindows上でオンに保ちつつ、輝度や描画内容だけを暗くするなら、Modern Standbyセッションの入口を避けられる可能性が高い。

類似事例

同じ症状 Framework Laptop利用者

SC_MONITORPOWERとNirCmdが本体スリープにつながる

Framework Laptop 16の利用者は、ショートカットで画面だけを消したいという同じ目的でSC_MONITORPOWERとNirCmdを試し、どちらもノートPC本体をスリープさせると報告している。解決済みの技術回答は得られていない。[7]

解釈

別のコマンドラインツールへ置き換えても、内部で同じWindows画面オフ経路を使う限り挙動は変わらない可能性が高い。

設計上の制約 Microsoft Q&A

Screen Offを継続状態として固定できないという相談

SleepStudyでScreen OffとSleepが交互に現れることを問題にした質問に対し、Modern Standbyは画面オフ後にSleepへ進む設計であり、設定だけでScreen Off状態を恒久維持する直接的な方法はない、という回答が受け入れられている。[8]

再現性に差 PowerToys Awake利用者

一般的な「Keep Awake」ツールにも機種差がある

Microsoft PowerToys Awakeは、システムを起動状態に保ち、必要なら画面もオンに保てる公式ツールである。一方、そのGitHub Issueには「indefinitely」でも後にスリープした、外部モニターではKeep screen onが効かなかった、という利用者報告がある。Issueだけでは原因は確定していない。[9][10]

含意

Power Request APIを正しく呼ぶだけで、すべてのOEM、モニター、電源ポリシーに同じ結果を保証できるわけではない。実機のSleepStudyとpowercfg /requestsが必要になる。

最近の利用者報告 ASUS ProArt利用者

画面オフとロック後の通常処理継続を求める例

別の利用者は、Windowsのスリープ設定を無効化してもロック画面の消灯後にS0 Sleepへ入ると報告している。同じ機種でも設定結果が異なるという返信があり、OEMユーティリティ、ロック状態、電源プランによる差が示唆される。これは仕様根拠ではなく、機種依存性を示す事例である。[15]

実際に試されている手段

1. 電源プランとSystemRequiredで画面オフ状態を延長する

Windowsの画面タイムアウトとシステムスリープタイムアウトを分け、PowerToys Awakeや独自のPower Requestでシステムスリープを防ぐ方法である。ACでは公式仕様と整合する。DCではタイムアウト後の上限があるため、長時間保証にはならない。[1][3][9]

2. DisplayRequiredで画面オンを維持し、最低輝度と黒表示を使う

画面オフイベントそのものを発生させず、WMIのWmiSetBrightnessで内蔵パネルの輝度を最低値へ下げる。黒い全画面ウィンドウを追加すれば、最低輝度が十分暗くない機種やOLEDの発光を抑えられる。ただしパネルと表示経路はオンのままで、物理消灯ではない。[5][11]

3. 外部モニターをDDC/CIで直接制御する

Windowsの論理画面状態を維持したまま、モニターへVCPコマンドを送る方法である。Twinkle Trayは任意VCPコードと電源状態の操作を提供し、MonitorianはDDC/CI能力を検査して対応モニターだけを操作する。既に多数の利用者がいる実装例だが、モニター、ケーブル、ドック、GPUドライバーへの依存が強い。[12][13][14]

4. Modern Standbyをレジストリで無効化する

コミュニティではPlatformAoAcOverrideなどの変更例が見つかるが、MicrosoftはS3とModern Standbyの切替をWindows上の設定変更としてサポートしていない。S3用ファームウェアがない機種では、スリープ不能、復帰不良、ドライバー問題を招く可能性があるためDisplayLightの製品機能には適さない。[6][15]

方式比較

「内蔵画面」「DCでのローカル処理」「機種非依存性」を同時に満たす方式はない。DisplayLightでは目的の異なる二つのモードへ分けるのが妥当である。

主要な発見

同じ目的を持つ利用者は複数存在する

長時間処理、WSL、ダウンロード、ロック後の処理を、画面オフのまま続けたいという相談は複数確認できた。特にModern Standby機では、従来PCで成立した「画面だけオフ」という前提が崩れることが共通の混乱点になっている。[7][8][15]

コマンド名を変えるだけでは解決しない

NirCmd、PowerShell、AutoHotkeyなどの「モニターをオフ」機能は、最終的にSC_MONITORPOWERまたは同等のWindows画面オフ経路を使う例が多い。ラッパーを変更しても、Windowsの電源状態遷移は同じになり得る。[7]

内蔵パネルの物理消灯には公開された汎用経路がない

Microsoftが公開している汎用手段は、画面状態の要求、内蔵画面の輝度変更、外部モニターのDDC/CI制御に分かれる。内蔵パネルだけを物理的に電源断し、OSには画面オンとして扱わせる共通APIは今回の調査では確認できなかった。これは「存在しないことの完全証明」ではなく、公開資料と代表的実装からの結論である。[5][11][12]

今回の11秒停止は追加診断が必要

2026年7月31日の実機ログでは、02:19:01にSC_MONITORPOWERでModern Standbyセッションが始まり、02:19:12にAdaptive Connected Standbyが通信を切断した。公式仕様のDC上限は最大5分であり、この差から、Power Requestが実際に有効だったか、AC限定が有効だったか、手動消灯が明示的待機として扱われたかを再確認する必要がある。[3][16]

DisplayLightへの提案

即時消灯と作業継続を別機能にする

現在の「ディスプレイをオフ」はWindows標準の即時消灯として残し、Modern Standbyでは作業継続を保証しない旨を表示する。別に「作業継続中は画面を暗くする」を追加し、DisplayRequired、SystemRequired、最低輝度、任意の黒表示を一つのライフサイクルで管理する。

モード開始前の輝度を保存し、必ず復元する

入力、利用者の解除、電源状態変更、アプリ終了、更新適用、例外発生時に元の輝度へ戻す。保存値はディスプレイごとに保持し、取得できなかった画面は変更しない。復元不能時は現在値と手動復旧方法を表示する。

外部モニターDDC/CIは能力検出後の任意機能にする

Monitorianと同様、対応能力を取得できたモニターだけを対象にする。既定では輝度変更までとし、電源VCPは実機確認済みのモニターに対する詳細設定へ限定する。DDC/CIの失敗をシステムスリープ防止の失敗へ連鎖させない。[12][13][14]

SC_MONITORPOWERを削除する前に比較試験を行う

手動消灯、自然なVIDEOIDLE、DisplayRequired＋最低輝度の3経路を、AC/DCとAC限定設定の組合せで比較する。Power RequestがOS側に見えていることを管理者権限のpowercfg /requestsで確認したうえで判断する。

リスクと制約

バッテリー消費と発熱

条件：画面を論理オンに保ち、CPUとネットワークを通常動作させる。
影響：Modern Standbyより大幅に電力を消費し、バッテリー切れ、性能低下、発熱が起こり得る。
緩和：残量警告、推定継続時間、温度・バッテリー低下時の安全解除を検討する。

輝度0が消灯を意味しない

条件：機種が公開する最低輝度が0より高い、または0でもバックライトが残る。
影響：暗室で光が見える、期待した節電にならない。
緩和：黒表示を併用し、「画面オフ」ではなく「最低輝度」と表現する。

DDC/CIで外部モニターが応答不能になる

条件：モニターがMCCSを不完全に実装している、ドックや変換器がコマンドを通さない。
影響：消灯後にソフトウェアから復帰できない、表示構成が変わる。
緩和：能力検出、機種単位の明示的オプトイン、物理ボタンによる復旧案内を必須にする。MicrosoftとTwinkle Trayの双方が互換性問題を警告している。[12][13]

黒画面はセキュリティロックではない

条件：黒いオーバーレイだけを表示する。
影響：入力や別のプロセスで画面内容が見える可能性がある。
緩和：ロックとの関係を別途設計し、「非表示」と「ロック」を同義にしない。

検証計画

  1. 基準取得：powercfg /aでS0 Low Power Idleを確認し、管理者PowerShellでpowercfg /requestsを記録する。
  2. 3経路比較：SC_MONITORPOWER、自然な画面タイムアウト、DisplayRequired＋最低輝度を各30分以上実行する。
  3. 条件分割：AC/DC、AC限定オン/オフ、ロック有無を混ぜずに一条件ずつ確認する。
  4. 実行継続確認：秘密情報を含まないローカルカウンターと疎通メタデータで、デスクトップ処理とネットワークの停止時刻を記録する。
  5. SleepStudy：powercfg /sleepstudyまたはSystem Power ReportでScreen OffとSleepの境界、Power Request、ネットワーク状態を照合する。
  6. 外部画面：DDC/CI対応能力、輝度変更、電源オフ、物理ボタンからの復旧をモニターごとに確認する。
  7. 採用判定：DCでCodexが継続し、入力・解除・終了・例外後に輝度とPower Requestが復元される場合だけ作業継続モードを製品化する。
次の最小実装：本番UIへ追加する前に、DisplayRequired＋SystemRequiredと輝度保存・復元だけを行う診断用スパイクを作り、このPCで30分のDC試験を行う。
