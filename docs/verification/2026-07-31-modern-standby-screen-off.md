# Modern Standby環境でのディスプレイ消灯経路と処理継続の実機確認

- 日付：2026年7月31日
- 環境：Windows 11、Modern Standby（S0 Low Power Idle、ネットワーク接続対応）
- 対象：DisplayLightの`SystemRequired`要求、手動消灯、自動画面オフ

## 目的

DisplayLightがスリープ防止要求を保持した状態でディスプレイが消えたとき、通常のデスクトップ処理とネットワーク接続が継続するか確認する。
`SC_MONITORPOWER`による手動消灯と、Windowsのアイドルタイムアウトによる自動画面オフを区別して比較する。

## 条件

- DisplayLightの`SystemRequired`要求だけを残した。
- PowerToys Awakeを無効化した。
- LocalSendを終了した。
- ChromeのVideo Wake Lockを解消した。
- `powercfg /requests`で、`DISPLAY`が「なし」、`SYSTEM`がDisplayLightだけであることを確認した。
- 電源プランはバランスで、システムスリープのタイムアウトはAC、DCともに「なし」だった。
- 2秒間隔の診断プローブで、時刻、経過時間、AC/DC、バッテリー残量、TCP接続成否だけをJSONLへ記録した。プロンプト、ファイル内容、認証情報は記録していない。

## AC駆動の結果

19時41分55秒に`SC_MONITORPOWER`によるイベント506が記録された。
約80秒後に誤ってタッチパッドへ触れて復帰したが、その間も診断プローブは約2秒間隔で連続して動作した。
通常時を含む最大記録間隔は3.218秒だった。

この確認範囲では、AC駆動時はDisplayLightの`SystemRequired`要求によって、画面消灯後も通常のデスクトップ処理が継続した。

## バッテリー駆動の結果

### `SC_MONITORPOWER`による手動消灯

実行前に`powercfg /requests`を再確認し、バッテリー駆動でもDisplayLightの`SystemRequired`要求が存在していることを確認した。

イベントと診断プローブの時系列は次のとおりだった。

| 時刻 | 観測内容 |
| --- | --- |
| 19:54:24 | `SC_MONITORPOWER`によるModern Standby開始イベント506 |
| 19:54:25 | 診断プローブ記録、ネットワーク成功 |
| 19:54:27 | 診断プローブ記録、ネットワーク成功 |
| 19:54:29 | 最後の診断プローブ記録、ネットワーク成功 |
| 19:54:36 | Adaptive Connected Standbyによりネットワーク切断 |
| 20:05:25 | ネットワーク再接続 |
| 20:05:26 | キーボード入力によるModern Standby終了イベント507 |
| 20:05:27 | 診断プローブが復帰し、完了を記録 |

最後の定期記録から復帰後の完了記録まで、実時間で657.623秒の空白があった。
画面消灯から約5秒後には通常のデスクトップ処理が停止し、約12秒後にはネットワークも切断された。
バッテリー残量は39%から38%へ変化し、途中にAC接続の記録はなかった。

### 1分タイムアウトによる自動画面オフ

同じくバッテリー駆動でDisplayLightの`SystemRequired`要求を保持し、WindowsのDCディスプレイタイムアウトを60秒に設定した。
`SC_MONITORPOWER`は使用せず、無操作のまま自動で画面が消えるのを待った。

20時14分56秒に、理由が`Idle Timeout`のModern Standby開始イベント506が記録された。
しかし、診断プローブは20時13分53秒から20時23分55秒まで601.098秒動作し、復帰操作より前に正常完了した。
最大記録間隔は3.02秒で、通常のデスクトップ処理が停止したことを示す空白はなかった。
20時24分22秒に、キーボード入力によるModern Standby終了イベント507が記録された。

TCP接続確認は284回中15回失敗したが、失敗は断続的で、その間もプローブは動作し、後続の接続確認は成功した。
連続したネットワーク切断やAdaptive Connected Standbyによる切断イベント172は観測されなかった。
バッテリー残量は35%から34%へ変化し、途中にAC接続の記録はなかった。

### 一時的な1秒タイムアウトによる消灯

「画面をオフ」操作への組み込み可能性を確認するため、バッテリー駆動時の`VIDEOIDLE`を1800秒から1秒へ一時的に変更した。
`STANDBYIDLE`とAC側の`VIDEOIDLE`は変更しなかった。

21時32分36秒に1秒を適用し、21時32分37秒に理由が`Idle Timeout`のModern Standby開始イベント506が記録された。
画面が消えたことを利用者が目視で確認した。

適用から約5秒後の21時32分41秒に、試験スクリプトがDC側の`VIDEOIDLE`を1800秒へ復元した。
復元時に画面は再点灯せず、21時33分23秒に利用者がキーボードで復帰させるまで消灯状態を維持した。
復帰後の読戻しでも、DC側が1800秒、AC側が300秒であることを確認した。

この試験では、短時間だけ`VIDEOIDLE`を1秒へ変更することで、`SC_MONITORPOWER`を使わずに自動画面オフを発生させられた。
画面が消えた後に元の値へ戻しても、画面は再点灯しなかった。

### v0.1.6 Portable版による確認

現在の作業ツリーから自己完結、単一ファイルの`v0.1.6` Portable版をVelopack 1.2.0で生成し、デバッガーを接続せずに起動した。
実行ファイルのファイルバージョンが`0.1.6.0`であり、Portable版の展開先から起動していることをプロセス情報で確認した。

バッテリー駆動のスリープ防止中にPortable版の「ディスプレイをオフ」を実行した。
22時27分50秒に、理由が`Idle Timeout`のModern Standby開始イベント506が記録された。
画面が消えている間もCodexによるREADME更新と標準検証が進み、22時40分29秒に利用者がキーボードで復帰させた。
画面オフから復帰までの時間は12分39秒だった。

復帰後もPortable版の同じプロセスが稼働していた。
DC側の`VIDEOIDLE`は変更前の1800秒、AC側は300秒であり、`display-off-recovery.json`は残っていなかった。
この確認により、試験スクリプトだけでなく`v0.1.6`の配布候補でも、設定の復元と画面オフ中の処理継続を確認した。

## 結論

この実機では、DisplayLightの`SystemRequired`要求が有効でも、バッテリー駆動中に`SC_MONITORPOWER`で画面を消すとModern Standbyへ移行し、通常のデスクトップ処理とネットワーク接続は継続しなかった。
同じ手動消灯でも、AC駆動中は今回の約80秒の確認範囲で処理が継続した。
バッテリー駆動でも、Windowsのアイドルタイムアウトによる自動画面オフでは、Modern Standby開始イベントが記録された後も診断プローブで10分間、`v0.1.6` Portable版で12分39秒、通常のデスクトップ処理が継続した。
さらに、`VIDEOIDLE`を1秒へ一時変更して5秒後に復元する方法でも、`Idle Timeout`による消灯と通常設定の復元を両立できた。

この結果から、イベント506や画面消灯だけでは、デスクトップ処理が停止したとは判断できない。
少なくともこの実機では、`SC_MONITORPOWER`による明示的な消灯と、アイドルタイムアウトによる自動画面オフで、その後の処理継続に差が生じた。
Modern Standby内部でどの状態遷移が異なったかは、この試験だけでは確定できない。
したがって、バッテリー駆動時にCodexなどのデスクトップ処理を確実に継続させる用途では、`SystemRequired`と`SC_MONITORPOWER`の組み合わせを保証手段として扱えないが、`SystemRequired`を保持したままWindowsの自動画面オフを待つ方式は有力な代替候補になる。
手動消灯試験の挙動は、以前の一晩の放置でCodexが`Reconnecting`になった現象と整合する。

## 制約と次の判断

- AC駆動の確認は約80秒であり、長時間継続の保証には追加試験が必要である。
- 自動画面オフの最長確認は12分39秒であり、一晩の処理継続や長時間のネットワーク安定性は未確認である。
- 次の段階では、自動画面オフ方式をバッテリー駆動で30分以上、可能なら一晩確認する。
- 一時変更の実装では、設定変更中の異常終了、電源プラン変更、AC/DC切り替え、外部からの設定変更を想定した復元処理が必要である。
- バッテリー駆動で処理継続を優先する場合は、論理ディスプレイをオンに保つ`DisplayRequired`と、最低輝度または黒画面表示を組み合わせる別モードを検討する。
- 外部ディスプレイのDDC/CI制御は機器依存のため、補助機能として分離して検討する。
- 利用者が明示したスリープ操作を妨げないこと、要求を確実に解放することは引き続き必要である。
